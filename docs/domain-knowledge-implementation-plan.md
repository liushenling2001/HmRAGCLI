# 领域知识编译系统实施推进建议

## 1. 文档目标

本文档用于把当前“领域知识精炼与智能体消费”方案转成分阶段实施计划，明确：

1. 哪些内容优先做
2. 哪些内容后做
3. 哪些现有流程不应被破坏
4. 各阶段的可交付结果

---

## 2. 总体原则

### 2.1 不推翻现有索引构建主流程

当前已有：

1. 数据源扫描
2. 文档解析
3. chunk 切分
4. knowledge unit 抽取
5. embedding 构建
6. 检索能力

这些能力继续保留，作为新系统的证据底座。

### 2.2 新系统作为上层新增能力

领域知识编译系统应作为现有系统上的上层模块，优先：

1. 复用已有证据对象
2. 新增领域和专题定义对象
3. 新增知识编译任务对象
4. 新增面向智能体的知识包对象

### 2.3 先做人定义，再做自动维护

不建议一开始就做自动归纳。优先顺序应该是：

1. 先让人定义领域和专题
2. 先做人工触发的领域编译
3. 人工流程稳定后，再做自动维护任务

---

## 3. 实施阶段

## 3.1 第一阶段：领域定义与专题定义

### 目标

让前端可以创建、查看、编辑领域和专题树。

### 后端新增

1. `domain_definitions`
2. `topic_definitions`
3. 基础 CRUD API

### 前端新增

1. 领域列表页
2. 领域新建/编辑表单
3. 专题树管理页

### 本阶段不做

1. 自动任务
2. 真正的知识编译
3. 智能体消费接口

### 可交付结果

1. 系统可以明确保存领域边界
2. 人工可以把后续知识维护目标定义出来

---

## 3.2 第二阶段：人工触发的领域编译

### 目标

实现：

1. 人工触发一个领域或专题编译任务
2. 基于当前证据库产出 `DomainBrief / TopicDossier / EvidencePack`

### 后端新增

1. `domain_refine_jobs`
2. `domain_briefs`
3. `topic_dossiers`
4. `evidence_packs`
5. 编译任务 API

### 编译流程建议

1. 根据领域/专题定义收集证据
2. 聚合相关 `documents / chunks / knowledge_units`
3. 调用高质量模型编译专题页
4. 为专题页绑定证据引用
5. 持久化结果

### 本阶段不做

1. 自动定时维护
2. 冲突自动发现的复杂逻辑
3. 全量智能体集成

### 可交付结果

1. 用户可以手工生成高质量领域知识页
2. 结果能回溯到底层证据

---

## 3.3 第三阶段：结论集合与冲突对象

### 目标

在专题页基础上，把知识拆成结构化结论和冲突对象。

### 后端新增

1. `claim_sets`
2. `conflict_sets`
3. 对应查询接口

### 实现重点

1. 让专题知识页不只是摘要文本
2. 明确结论、例外、冲突和时序
3. 为智能体提供更结构化的消费对象

### 可交付结果

1. 智能体可以读取“结论集合”而不是只读长摘要
2. 系统能显式表达冲突信息

---

## 3.4 第四阶段：正文回查与智能体消费 API

### 目标

支持智能体：

1. 获取领域知识包
2. 读取专题页
3. 拉取正文上下文

### 后端新增

1. `memory-pack` API
2. `evidence/expand` API
3. `quote/context/section` 三种回查模式

### 实现重点

1. 精炼层不替代原文
2. 智能体需要时可以直接拿到适合写作的正文上下文

### 可交付结果

1. 智能体先认知，后回查，最后生成
2. 形成稳定的写作与分析工作流

---

## 3.5 第五阶段：自动领域维护

### 目标

对已定义领域执行自动增量归纳和维护。

### 后端新增

1. 自动调度任务
2. 领域变更检测
3. 增量编译策略

### 实现重点

1. 自动任务只处理已定义领域
2. 自动结果优先作为 `maintained` 或 `draft`
3. 不直接覆盖人工高质量结果

### 可交付结果

1. 领域知识页持续保持新鲜
2. 自动维护和人工精炼形成互补

---

## 4. 优先推荐路径

如果按最小可用版本推进，推荐顺序如下：

1. 先做领域/专题定义
2. 再做人工触发的专题编译
3. 再做证据包与正文展开
4. 再做结构化结论和冲突
5. 最后做自动归纳

原因：

1. 领域边界未定义时，自动任务没有稳定目标
2. 人工流程更容易验证“专题编译”是否真的有价值
3. 证据回溯能力是给智能体使用的关键基础
4. 自动维护应建立在人工流程稳定之后

---

## 5. 当前项目中不建议立即修改的部分

当前阶段不建议直接重做：

1. 扫描流程
2. 解析流程
3. chunk 切分逻辑
4. knowledge unit 抽取 schema
5. 当前搜索接口主逻辑

这些功能应先作为底层稳定输入保留。

---

## 6. 与现有检索接口的关系

现有检索接口继续保留，承担：

1. 原文检索
2. 底层证据检索
3. 编译任务的证据收集入口

未来新增的编译式接口承担：

1. 领域总览获取
2. 专题知识页获取
3. 结论集合获取
4. 正文回查

因此，新的领域知识编译系统不是替代检索系统，而是建立在其上的“知识组织层”。

---

## 7. 建议近期直接推进的产物

如果下一步开始开发，建议直接进入以下可交付物：

1. DDL 草案确认
2. Java DTO 草案
3. API 请求响应模型草案
4. 前端领域配置页信息架构
5. 人工编译任务状态机

---

## 8. 最终结论

本设计建议按“定义 -> 人工编译 -> 证据回查 -> 智能体消费 -> 自动维护”的顺序推进。

这样可以最大程度：

1. 控制风险
2. 保持现有系统稳定
3. 验证领域编译的真实价值
4. 为后续自动归纳留出稳定基础
